## 2. 记忆系统（怎么实现）

### 2.1 三条硬决定

| # | 决定 | 理由 |
|---|---|---|
| M1 | **记忆存在 PG 的 `memory` 表，不做向量库** | 单用户、量级几百条；关键词 + 最近即可命中。等 M3 再上 pgvector |
| M2 | **写入用「回合后抽取」**，不给模型开 `memory_save` 工具 | ① DeepSeek 原生搜索一轮里不能再声明别的工具（官方限制）；② 抽取失败不影响回答，回答不会为了「存记忆」被打断 |
| M3 | **读取在回合前注入**（约 6 条），并把用到的 id 记到该条回复上 | 这样「根据记忆生成」这句是**可核查的事实**，不是模型自称 |

### 2.2 表

```sql
memory(
  id, text, kind,            -- kind: fact（学习事实）/ pref（偏好）
  subject,                   -- 可空；九科之一
  source_message_id,         -- 从哪句话抽出来的
  created_at, last_used_at, use_count,
  status                     -- active | archived
)
-- message 增量
message.sources        JSONB  -- [{type:'memory'|'web', id?, text?, title?, url?, snippet?, site?}]
message.tools          JSONB  -- ['web_search']（本轮用到哪些工具，去重）
message.remembered     JSONB  -- [{id,text,kind}] 本轮新写入的记忆
```

### 2.3 抽取规则（写入）

- 时机：回答 `done` 之后异步跑；**不阻塞正文**。
- 调用：同一个 provider/model，非流式，`max_tokens 300`，要求输出严格 JSON：
  `{"memory":[{"text":"…","kind":"fact|pref","subject":"物理"}]}`
- 过滤：≤ 40 字、必须是一句稳定事实/偏好；与已有记忆做**文本相似度去重**（字符级 Jaccard > 0.7 视为重复）。
- 每轮最多 2 条；解析失败就**不写**（宁可漏，不可脏）。

### 2.4 读取规则（注入）

- 取 `status=active` 中：与用户本轮文本有 2-gram 交集的（最多 6 条）+ 最近 7 天用过的（最多 2 条），去重后 ≤ 8 条。
- 注入到 system prompt 末尾：
  ```
  你记得的关于她的事（不是本轮说的，是长期的）：
  - …
  ```
- 命中的 id 全部记入 `message.sources`（type=memory）。界面据此显示「根据 N 条记忆」。

### 2.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/memories?limit=50&cursor=` | `{items, next}` |
| PATCH | `/api/v1/memories/{id}` | 改 `text` / `status`（archived 即软删） |
| DELETE | `/api/v1/memories/{id}` | 真删（单用户，允许） |
| GET | `/api/v1/memories/stats` | `{total, active, used_last_7d}` |

## 3. 联网搜索

### 3.1 设置项

`app_setting` 键 `search`：
```json
{"enabled": false, "provider": "deepseek", "api_key": "", "max_results": 5}
```
`provider` ∈ `deepseek`（原生）/ `tavily` / `bocha`。

| provider | 协议 | 说明 |
|---|---|---|
| `deepseek` | 服务端工具 `deepseek_web_search` | 复用当前 provider 的 key；**该轮不能再声明别的工具** |
| `tavily` | `POST https://api.tavily.com/search` | 需要 key |
| `bocha` | `POST https://api.bochaai.com/v1/web-search` | 需要 key |

| 方法 | 路径 |
|---|---|
| GET/PATCH | `/api/v1/settings/search`（PATCH 后立即生效） |
| POST | `/api/v1/settings/search/test` → `{ok, latency_ms, error?}` |

### 3.2 原生路径（DeepSeek）

请求里加：
```json
"tools": [{"type": "deepseek_web_search"}]
```
流式解析扩展字段 `delta.server_tool_event`：`call_started`（带 action.queries）/ `call_completed`（带 sources）。
`sources` 每项 `{title,url,snippet,site_name}` → 写入 `message.sources`（type=web）。
**限制**：启用原生搜索的那一轮，不注入其他工具。

### 3.3 函数路径（tavily / bocha）

- 声明 `web_search` 函数工具，模型调用 → 服务端检索 → 结果回填 → 继续生成（最多 3 轮）。
- 结果同样写入 `message.sources`。

## 4. SSE 增量（与 v1 兼容，只加不改）

| type | 载荷 | 时机 |
|---|---|---|
| `tool` | `{name:"web_search", state:"start"/"end", count, sources:[…]}` | 工具调用前后 |
| `memory` | `{items:[{id,text,kind}]}` | 抽取完成（`done` 之后） |
| `done` | 追加 `{tools:[…], sources:[…], remembered:[…]}` | 结束 |

> `done` 先发（回答完就结束等待），`memory` 后发；前端收到 `memory` 再把胶囊补到该条消息上，不要阻塞正文。

| 项 | 判定 |
|---|---|
| 记忆写入 | 说一句「我用右手写字」，下一轮结束 `memory` 表 +1，且该条消息显示「记忆 +1」 |

## 7. 修订（2026-11-14 晚）：分步时间线

用户反馈「干改完之后看不到思考过程了，应该分步展示：思考完再调用工具再搜索」。开源做法一致：

| 来源 | 做法 |
|---|---|
| [Vercel AI SDK 4.2](https://ai-sdk.dev/v4/docs/migration-guides/migration-guide-4-2) | tool calling 不再拆成多条消息，而是**一条消息多个 part**（reasoning / tool / text 交错） |
| [assistant-ui chain-of-thought](https://www.assistant-ui.com/docs/guides/chain-of-thought) | 用 `GroupedParts` 把相邻的 reasoning + tool 合成一个可折叠的「思考」区 |
| [Chainlit Step](https://docs.chainlit.io/concepts/step) | 每步一个 step 对象（input/output + start/end），`cot` 档位决定显示 full / 仅工具调用 |

### 7.1 数据

新列 `message.parts JSONB`，有序数组：

```json
[
  {"type":"reasoning","text":"…","ms":1200},
  {"type":"tool","name":"web_search","kind":"search","queries":["今天新闻"],"count":1},
  {"type":"reasoning","text":"…","ms":800},
  {"type":"text","text":"最终回答"}
]
```

### 7.2 SSE 增量

| type | 载荷 | 时机 |
|---|---|---|
| `part` | `{kind:"reasoning"|"tool"|"text"}`（tool 另带 `queries`） | 新一段开始 |
| `part_end` | `{kind:"reasoning"}` | 该段思考结束（DeepSeek 的 `step_reasoning_done`） |
| `part_update` | `{kind:"tool"}` | 工具结束（计数 +1） |
| `done` | 追加 `parts` | 结束 |

### 7.3 界面

```
⚡ 思考 1 秒                                   ⌄
🔍 联网搜索「今天新闻」                     1 条 ›
⚡ 思考 8 秒                                   ⌄
[🔍 搜索 1 次]
最终回答…
[db] 根据 2 条记忆 · [globe] 参考 1 个网页     ›
```

- 每段思考可展开看原文；默认折叠但**行本身始终可见**，所以「先思考、再搜索、再思考」的顺序一眼能看出来；
- 工具行可点，打开来源浮窗；
- 只有一段思考且没有分段耗时（非 DeepSeek 原生路径）时，用整轮 `thinking_ms` 兜底；
- 没有 parts 的旧消息仍走原来的折叠思考条（向后兼容）。

## 8. 修订二（2026-11-14 深夜）：工具收进折叠 / 记忆独立页 / 记忆质量

用户反馈三条，逐条落：

### 8.1 工具调用与搜索收进折叠的「思考 N 秒」

不再单独列工具行。**一个折叠块**，头部 `思考 12 秒 · 搜索 2 次 · 记忆 +1`，展开后按时序排：思考正文 → 联网搜索（可点开来源）→ 再思考 → 记住「…」。样式统一：同一字号 `s5`、同一颜色 `ink2`、同一左对齐、工具行只在可点时用 `chevron-right`。
（对齐 assistant-ui 的 `GroupedParts`：把相邻 reasoning + tool 归成一个可折叠区。）

### 8.2 记忆是独立页面（L0）

- rail「记忆」可点，进入 L0 记忆页；**设置页不再有记忆组**；
- 记忆页：标题 + 条数、`收录 / 自动记忆` 开关、列表（正文 + `事实/偏好 · 时间` + 删除）；
- 空态给一个动作（返回对话）。

### 8.3 记忆为什么「不好用」以及修法

| 症状 | 根因 | 修法 |
|---|---|---|
| 问天气也显示「根据 2 条记忆」 | 检索带「最近 2 条」兜底，无关也注入 | **只注入相关**：至少命中 2 个 2-gram；无命中就一条不注 |
| 用户说「记住我爱吃蛋糕」没落库 | 抽取规则过严、且把偏好当闲聊 | **显式「记住…」最高优先级**，必抽，kind=pref |
| 抽出一堆碎话 | prompt 没给「绝不记」清单 | 明确列绝不记：闲聊/情绪/一次性问答/模型自己的话/题目内容；多数对话应返回空数组 |
| 模型不知道今天几号 | system prompt 没日期 | 每轮注入「今天是 YYYY 年 MM 月 DD 日」 |

## 9. 缓存（KV Cache）：为什么要这样摆 prompt

依据：
- [DeepSeek 上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)：默认开启、**按前缀命中**、按固定 token 间隔落盘；`usage.prompt_cache_hit_tokens / prompt_cache_miss_tokens` 可读。
- [Open WebUI · Prompt Caching 优化](https://docs.openwebui.com/features/chat-conversations/prompt-caching/)：**静态前缀（system + tools）+ append-only 增长 + on-demand retrieval**，不要每轮把 RAG 模板重新塞进 system 或最后一条消息。
- [Open WebUI #20317](https://github.com/open-webui/open-webui/pull/20317)：把「很少变」的上下文放进 system 以保住前缀缓存。

### 9.1 三条硬规则（已落到代码）

1. **system 只有静态内容 + 很少变的记忆块**（`SYSTEM_PROMPT + today_line + memory_block`）。记忆只在「命中相关」时才出现，多数轮次为空 → 前缀不变。
2. **历史 append-only**：每轮请求 = 上一轮请求 + 新内容。**禁止滑动窗口**（`limit(20)` 会每轮丢掉最旧消息，整条前缀失效）。超预算才从最旧丢，且用 token 预算而不是条数。
3. **网页资料不进历史、不进 system**：DeepSeek 走服务端工具（append-only 的工具结果由 API 管）；Tavily/博查走函数工具循环。上下文一律不塞进用户消息。

### 9.2 实测

| 场景 | 单轮命中率 |
|---|---|
| 受控：长静态前缀 + append-only（直接调 DeepSeek） | 第 2 轮起 **90–95%** |
| 用本项目真实 prompt 构造（前 20 条历史）模拟 | 第 2 轮起 **98%** |
| 修复前（滑动窗口 + 注入 + 错误轮次不进历史） | **41%** |

**注意**：整体命中率会被首次请求（必然全 miss）和超长回答拉低；要对齐 95%，需要**干净的、连续的会话**。当前开发库里混了 200 条测试消息、其中多轮是失败请求（status=error 不进历史），前缀天然对不齐——这不是架构问题。

### 9.3 读取命中率

`GET /api/v1/stats/cache?limit=20` → `{requests, hit_tokens, miss_tokens, hit_rate, recent[]}`；每条 assistant 消息也存了 `cache_hit_tokens / cache_miss_tokens`。

## 10. 更正：原生搜索与函数工具可以并存（2026-11-15 实测）

之前文档里写「声明 `deepseek_web_search` 时不能同时声明别的工具」，**这个结论是错的**。拿真实 key 实测：

| tools 声明 | 结果 |
|---|---|
| 只 `deepseek_web_search` | HTTP 200 |
| `deepseek_web_search` + function `memory_search` | **HTTP 200** |
| 只 function | HTTP 200 |

DeepSeek 文档里那句 `other tools cannot be used together with ...` 指的是**其它服务端工具**（`deepseek_read_url`/`safety_check`/`title` 一类），**不包含 function 工具**。

### 10.1 所以架构合并为一条

- 一律走函数工具循环（`stream_with_tools`）；
- `server_tools` 参数叠加 `{"type": "deepseek_web_search"}`（开启原生搜索时）；
- 函数工具包含 `memory_search`，非 DeepSeek 搜索时再加 `web_search`；
- **记忆不再自动注入**（system 完全静态），改由模型按需调用 `memory_search` —— 这就是 Open WebUI 说的 on-demand retrieval。
- 工具是按需调用：词面对不上时给最近几条兜底，避免「模型来查却空手而归」。

### 10.2 澄清：底层不是 Pi

MVP 是**直连 OpenAI 兼容 HTTP**（`docs/21` 决策 M2），Pi 要到 M4 才接。本文里所有「provider 限制」都是 DeepSeek API 的限制，与 Pi 无关。接 Pi 后，工具由 Pi 的 harness 调度，同一限制依然存在（provider 侧）。

## 11. 记忆的工具集与记忆页（2026-11-15）

### 11.1 agent 可用的记忆工具

| 工具 | 作用 | 安全边界 |
|---|---|---|
| `memory_search` | 按需检索（问她的情况、要个性化建议时自己调） | 只读 |
| `memory_add` | 记住一件事（用户说「记住…」或出现稳定事实/偏好） | 写入前**去重**：相似度 > 0.6 只更新不新增 |
| `memory_update` | 修正记错的内容（先 search 拿 id） | 只改指定字段 |
| `memory_delete` | 忘掉一条（先 search 拿 id） | **归档不是硬删**，界面上消失但可恢复 —— 符合 AGENTS「不可逆操作不给 agent 开工具」 |

实测：`记住：我不吃香菜` → 模型调 `memory_add`，写入「她不吃香菜，不要推荐含香菜的菜」；连说三次只留一条（去重生效）。

### 11.2 记忆页（L0）

- 顶部：`添加记忆` + `自动记忆` 开关；
- 分组：**关于她**（pref：画像/偏好） + **学习**（fact：带学科）；
- 每行：正文 + `类型 · 学科 · 时间 · 用过 N 次`，整行可点；
- 点开 = 编辑浮层：内容（多行）+ 类型（事实/偏好 分段）+ 学科 + 删除/取消/保存；
- 空态给「添加记忆」动作。

### 11.3 回到底部

上翻超过 240px 时，输入框右上出现 44×44 圆形按钮，点击平滑回到底部并恢复自动跟随（`state.stick = true`）。

## 12. 学科空间与上下文压缩（2026-11-15）

### 12.1 学科空间（按 docs/11 落地）

- **关系轴单一、内容轴分科**：十条长期对话（`全部` + 九科），每条是 `conversation.subject`；
- 顶部学科胶囊点开 → 十项，当前项带勾、右侧显示该科消息数；
- 切换 = 换空间（`PATCH /subject`），不是新建对话；**每个空间的滚动位置各自记住**；
- 记忆 / 记忆页 / 模型配置 **全局共享**（不按科拆）。

接口：`GET /subjects` → `{current, items:[{subject,count}]}`；`PATCH /subject` → 切到该空间。

### 12.2 上下文压缩（递归摘要 + 保留最近）

参考：Claude Code 的 autocompact（超阈值总结后继续，先落盘完整 transcript）· MemGPT/Letta（FIFO 逐出最旧约 50%，递归摘要替代）· Open WebUI（超阈值总结较早部分，保留比例夹在 10–50%）。

**我们的做法**

| 项 | 规则 |
|---|---|
| 完整历史 | `message` 表**永不删除**（数据主权）；压缩只影响「送进模型的那部分」 |
| 触发 | 未压缩消息的估算 token 超过 `history_token_budget`（默认 110k） |
| 压缩量 | 从最旧开始，压到剩余约 `KEEP_RATIO=35%`，但至少保留 6 条原文 |
| 摘要 | 同一模型非流式生成，≤500 字，固定三段：主题与结论 / 稳定事实与偏好 / 待跟进 |
| 存放 | `conversation.summary_md` + `summary_until_seq`（单调游标） |
| 注入 | 作为第二个 `system` 消息，放在静态 system 之后；**只在压缩时变化**，日常缓存前缀不受影响 |
| 游标 | 新增 `message.seq`（Identity，单调递增）——`created_at` 会撞（同一批插入），不能当游标 |

实测：20 条对话、预算压到 200 token → 压缩 14 条成 198 字摘要、保留 6 条原文，之后 `history()` 返回 6 条 + 非空摘要；摘要确实出现在第二个 system 消息里。

## 15. 更正 §10：原生服务端工具**不能**和函数工具同轮（2026-11-15 复测）

§10 里我写「实测可以并存」，**那个结论是错的**。当时只看 HTTP 200 就下了判断，没有验证工具是否真的被注册。

复测证据：
- 混合声明（`deepseek_web_search` + 4 个 function 工具）→ 请求 200，但**模型自述「工具列表里没有搜索」**，且全程 0 次 `server_tool_event`、0 条来源；
- 只声明 `deepseek_web_search` → 同一句「今天有什么新闻？」产生 **8 次工具事件、19 条来源**。

结论：混合时服务端工具被**静默忽略**（不报 400，只是不生效）。DeepSeek 文档那句「other tools cannot be used together」按效果是成立的。

### 15.1 现在的两条路径

| 条件 | 路径 | 记忆 |
|---|---|---|
| 联网搜索开 + provider 是 DeepSeek | 单次请求，只声明 `deepseek_web_search` | **system 注入**（只注相关，多数轮为空） |
| 其它（含搜索关） | 函数工具循环：`memory_search/add/update/delete`（+ 非 DeepSeek 的 `web_search`） | 模型按需调用 |

实测：
- 搜索关 → 问「我爱吃什么」：调用 `memory_search`，来源 `['memory','memory']`，回答「你爱吃蛋糕」；
- 搜索开 → 问「今天有什么新闻」：8 次 `web_search` 事件、19 条来源。

> 教训记下来：**判断一个工具是否生效，不能只看 HTTP 状态码**；要么看返回里的 usage/事件，要么让模型自述工具列表。

## 16. 搜索改用 DeepSeek Search API 自建工具（2026-11-15）

用户指出：DeepSeek 有新版的搜索 API，直接封成自己的工具即可，不必受「服务端工具不能混用」的限制。

接口（官方文档 [网页搜索与抓取](https://api-docs.deepseek.com/zh-cn/guides/search/)）：
- `POST https://api.deepseek.com/v1/tools/search`，Bearer 鉴权
- 请求 `{query, count(1–50), ori_question?, need_content?}`
- 响应 `results[] = {title,url,snippet(100–200字),summary(600–800字),content,site_name,date,authority,rerank_score}`
- 计费：**5 元 / 1000 次成功请求**（按请求，不按 token 或结果数）

### 16.1 落地

- `search.py` 新增 `_deepseek()`，与 tavily/bocha 共用 `search(provider, key, query, n)` 入口；
- `web_search` 成为**普通函数工具**，与 `memory_search/add/update/delete` 同轮可用；
- provider 选 `deepseek` 时，key 复用当前模型 provider 的 API Key；结果写进 `message.sources`（title/url/snippet/site/date）；
- **不再走 `deepseek_web_search` 服务端工具**（那条路与函数工具互斥）；
- 设置页「测试」对 DeepSeek 走真实 Search 请求。

实测：问「今天有什么新闻」→ 调用 `web_search`，`done.sources` **5 条真实来源**，回答带当天日期与新闻内容；单次工具耗时约 1–2 秒。

### 16.2 首页回到「今天」

之前启动会恢复上次的学科（所以看不到今日首页）。现在 `boot()` 先 `forceToday()`（PATCH 当前空间为「全部」），再加载会话与概览——**打开就是今天**，点某科才进该科。
