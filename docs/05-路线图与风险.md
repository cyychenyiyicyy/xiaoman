## 1. 六个里程碑（按依赖排序，不按功能清单）

每个里程碑的判据是「**能用了**」，不是「写完了」。

| # | 里程碑 | 交付物 | 验收（你自己能验） | 预估 |
|---|---|---|---|---|
| **M0** | **骨架** | monorepo、docker-compose 起得来、8 张表建好、Android 空壳能装、GitHub Actions 出第一个签名的 APK | 手机装上 App 能打开；服务器 `curl /health` 返回 ok；推 tag 能出 APK | **1 周** |
| **M1** | **录入闭环** ★关键路径 | 拍 → 上传 → OCR → 切题 → LLM 组装 → 人工确认 → 入库 | **拍 10 页卷子，20 分钟内全部变成结构化题目**（含你确认耗时） | **2–3 周** |
| **M2** | **复习闭环** | FSRS 调度 + 每日队列 + 四档评分 + revlog + 首页 | 连续 7 天打开 App 都有队列；评分后 due 正确变化 | **2 周** |
| **M3** | **知识关联** | 知识点树导入 + 题目标注 + 先修边 + 掌握度聚合 + 图谱视图 | 能回答「我电磁感应老错，根因在哪」且给出先修链 | **2–3 周** |
| **M4** | **提问沉淀** | Pi 网关 + 流式 + ~20 个学习工具 + 自动沉淀 + 引用溯源 | 问一次 AI，3 秒后库里多出 1–3 个待复习项 | **3–5 天** |
| **M5** | **主动与统计** | ntfy 推送 + 周报 + 热力图 + 遗忘预警 | 周日收到周报；断签 3 天只提醒一次 | **1–2 周** |
| **M6** | **打磨（长期）** | 全量导出（apkg + JSON）、离线队列预下发、恢复演练、备份监控 | 抽一天备份能恢复到另一台机器 | 持续 |

**业余时间（每周 8–10 小时）口径：到 M2 约 6 周，到 M5 约 3 个月。**

### 关键路径只有一条

**M1 录入闭环是整个项目的生死线。** 理由：M2/M3/M4 在没有数据的时候都能靠假数据开发，但**没有真实录入，你就不会用；你不用，这个项目就死了**。所以：

- M1 不完成，不要开始做图谱可视化（最容易沉迷的部分）；
- M1 的验收标准是**真实跑通 10 页**，不是「代码写完了」。

> 这也是为什么 §1 建议「OCR 先用云 API」：本地 GPU 那套环境搭建（CUDA/cuDNN/模型下载）能耗掉两个周末，而它不改变任何产品能力。

按「发生概率 × 后果」排序，每条都给**已定的对策**（不是「注意一下」）。

| # | 风险 | 概率 | 后果 | 对策 |
|---|---|---|---|---|
| **R1** | **Pi 破坏性更新**打乱节奏 | 高 | 中 | ① **锁精确版本**（`1.5.2`），不跟 latest；② **网关只依赖 4 个 API**（`createAgentSession / subscribe / prompt / getEntries`），接口面越小升级越无痛；③ 升级前在 git worktree 里跑一遍冒烟验收 |
| **R2** | **录入太麻烦 → 你不用 → 项目死** | 高 | 致命 | ① M1 验收标准定死「20 分钟内 10 页」；② 首屏只留一个 `＋拍一页`；③ 允许「先存图、后补字段」；④ 批量拍 + 后台跑 + 可离开 |
| **R3** | **OCR 对试卷/手写准确率不够**，产出脏数据 | 高 | 高 | ① **人工复核队列必须有**（置信度低于阈值必进）；② 不自动合并/不自动改已确认字段；③ 手写答案区默认不识别，只存图 |
| **R4** | **数据丢失** | 低 | 致命 | ① 每日 `pg_dump` + 异地；② **每月恢复演练一次**；③ 图片单独存对象存储并双副本；④ 全量导出随时可跑 |
| **R5** | **单人维护倦怠**（三个月后不想动） | 中高 | 高 | ① 不做多用户/不做社交/不做游戏化（见 01 §6）；② M2 之后每个里程碑都能独立交付价值，随时可停；③ 每周固定时段，不追进度 |
| **R6** | **图谱过度设计**（沉迷可视化） | 中高 | 中 | ① 先只做三层（章/节/知识点）；② 图谱视图放 M3 末尾，甚至可以砍；③ 节点 > 300 才需要聚合，先别想 |
| **R7** | **国内网络**：手机连不上服务器 | 中 | 高 | ① 服务器放国内（你已有 `e1e.site` 与 CF 经验）；② **不要只依赖 Cloudflare**——你的 yi-ai-class 已记录「国内存在墙中墙」；③ 备用：局域网直连 + 对象存储默认域名；④ 走 **HTTP 明文 80 端口的连通性自检**先分清是 DNS/SNI/链路哪一类 |
| **R8** | 模型成本失控 | 低中 | 中 | ① 默认 `deepseek-v4-flash` 闲时；② **长系统提示必须开缓存**（命中价可低至 ¥0.15/1M）；③ 问答历史做 compaction，别全塞 |
| **R9** | **依赖腐烂**（两年后装不上） | 中 | 中 | ① 锁 lockfile；② **季度升级窗口**，一次只升一个组件；③ 记录 ADR（为什么选它）；④ 最小依赖：后端直接依赖不超过 5 个 |
| **R10** | **Android 开发者验证**（2027 全球）拦自装 APK | 中 | 中 | 现在就注册开发者身份；自用场景通常不被拦，但**包名先占住**是零成本的保险 |

## 4. 「永久项目」的含义：四条工程纪律

你说「可持续可维护的永久性项目」。这句话不能只写进 README，要变成四条可执行的规矩。

### 4.1 数据契约优先于代码

**代码会重写，数据要活十年。**

- 所有表带 `schema_version`，任何变更走**迁移脚本**（Alembic），不手改；
- **导出是一等功能**，不是附属功能：`GET /export/full` 随时能产出 `json + markdown + 图片` 的完整包，能脱离这个系统被读懂；
- **阿基里斯之踵的解法**：只要数据能导出成 Markdown + apkg，**这个项目就永远不会变成你的负担**——真做不下去了，进 Anki 继续复习。这条写进 README 第一行。

### 4.2 不追新

- `android/build.gradle.kts` 用 **version catalog + 精确版本**，不用 `+` 或 `latest.release`；
- Python 用 `uv.lock` / `poetry.lock`；
- **季度升级窗口**：一次只升一个组件，升完跑验收。**不要**看到新版本就升。
- 明知会变的（Pi、`material3` 1.5 的 Expressive）**等它们 stable 再用**。

### 4.3 验收要能失败（这条你自己踩过坑）

你我 workspace 的 `AGENTS.md` 里记着这个教训：*skin-verify 从不设退出码，报告里 31 个 FAIL 却 exit 0，于是"验证通过"地把坏包上线了。*

这个项目照抄这套纪律：

```
server/tests/verify.py    → 结尾 process.exit(failures ? 1 : 0)
                          → 开跑前先删旧报告（崩在半路会残留上次结论）
                          → 人工复核时打开报告看内容，别只看退出码
```

至少四条自动验收：
1. **调度正确性**：给定 100 条 revlog，重算后 due 与 py-fsrs 一致；
2. **迁移可回滚**：`upgrade → downgrade → upgrade` 三次不报错；
3. **导出完整性**：导出 → 干净库导入 → 数据条数与校验和一致；
4. **APK 可安装**：签名的 APK 过 `apksigner verify`。

### 4.4 文档即代码

```
docs/
 ├ ARCHITECTURE.md      架构图 + 进程职责（04 那张图）
 ├ DECISIONS/            ADR：0001-为什么不用 Neo4j.md、0002-为什么 Pi 隔离成子服务.md
 ├ DATA_MODEL.md        8 张表 + 迁移历史
 └ API.md               由 OpenAPI 自动生成，不手写
```

**ADR 的写法只要三行**：背景 / 决定 / 代价。它的作用是——**三年后你不记得为什么这么写时，能自己说服自己**。

## 6. 和你的其他项目的关系

你已有 `yitie`/`open-yitie`（教室作业看板）、`yi-ai-class`（课堂录播 → 总结 → 提取作业）、`classboard`。这个项目和它们的关系：

| | 关系 | 可复用 |
|---|---|---|
| `yitie` / `classboard` | **无关**。一个面向教室大屏，一个面向你自己 | 可复用：Cloudflare 部署套路、更新通道设计 |
| `yi-ai-class` | **有交集**：它已经在做「录播 → 转写 → 总结 → 提取作业」，**转写与结构化那套 pipeline 可以直接搬** | ★ **转写/总结的 prompt 与清洗逻辑**、`netcheck.py` 的网络诊断、FunASR/SenseVoice 的静态二进制经验 |
| `open-yitie` | 已开源过、有 README/许可证/CI 经验 | 仓库规范、MIT 许可证模板 |

**建议**：`yi-ai-class` 的转写层如果已在真机验证通过，本项目 M1 的「语音/长音频资料 → 文字 → 知识点」可以省掉大半工作。
