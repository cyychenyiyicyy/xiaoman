# 06 · AI 运行时与工具设计（Pi 作为底层框架）

> 本文修正 04 §3 的结论：**Pi 是这套系统的 AI 运行时/框架本身，不是一个「可选子模块」。**
> 事实依据：pi.dev 官方文档 `models` 页（2026-11 实测）+ 前轮调研的 SDK/RPC/packages/sessions 各页。

---

## 1. 先认账：上一版把 Pi 写窄了

我上一版写的是「Pi 只做对话大脑，不做系统内核」，这句话容易被读成「Pi 帮不了你多少，AI 那层你还是要自己搭」。**这个读法是错的，而且我的措辞有问题。**

准确的说法是：

> **Pi 承担全部 AI 底层。你只写三样东西：界面（Android）、工具（让 agent 能读写你的学习库）、薄网关（让手机能连上它）。**

而且我上一版担心的「Pi 没内置记忆」这件事，在你这个架构里**根本不是问题**——理由见 §4，这反而是最关键的一条设计洞见。

---

## 2. Pi 帮你做掉的（这些你一行都不用写）

| 层 | Pi 提供 | 你原本要自己写的 |
|---|---|---|
| **对话循环** | 完整 agent loop：流式输出、tool_call 解析与执行、多轮、中止、steer/followUp | 最容易写崩的那 1500 行 |
| **Provider 抽象** | 15+ provider、数百模型，协议层统一在 `pi-ai`：`anthropic-messages` / `openai-completions` / `openai-responses` / `azure-openai-responses` / `pi-messages` | 每家一个适配器，无底洞 |
| **模型目录（这是你说的那点）** | **自带 bundled catalog，并可从 pi.dev 覆盖更新**——含 provider、model ID、能力、上下文长度、价格。离线有缓存，`pi update --models` 强制刷新 | 自己维护一张模型表 + 定价表 |
| **鉴权/凭据** | `/login` 存 `auth.json`，或走环境变量；凭据来源有明确优先级（`--api-key` > `auth.json` > `models.json` 的 `apiKey` > 环境变量/云凭据） | 又一套密钥管理 |
| **自定义端点** | `models.json` 填 `baseUrl` + `api` + `models`，任何 OpenAI/Anthropic 兼容端点（Ollama/LM Studio/vLLM/SGLang/中转）都能接；`$NAME`/`${NAME}` 环境插值、`!command` 取密钥 | 自己写兼容层 |
| **成本与限流细节** | `promptCache: {short, long}` 声明缓存寿命（缓存命中能把你成本打到 1/10）；`inputLimits.images.resize` 控制图片编码尺寸/字节数（**题目照片正好用得上**）；`inputLimits.maxRequestBytes`、`images.maxPerMessage` | 自己算 token、自己压图 |
| **上下文管理** | compaction（`reserveTokens 16384` / `keepRecentTokens 20000`，可按模型覆盖）+ 分支摘要 | 自己写裁剪策略 |
| **会话持久化** | append-only JSONL 树，`/tree` `/fork` `/clone` 不丢历史；`sessionDir` 可指到持久卷 | 自己设计会话存储 |
| **扩展/打包** | `pi install npm:|git:|本地路径`，一个 package 内含 `extensions/ skills/ prompts/ themes/`；skills 按 description **惰性加载**，省 token | 自己搭插件体系 |
| **嵌入方式** | TS SDK（进程内 `createAgentSession()`）、RPC（stdio JSONL）、JSON 事件流、print | 自己设计 IPC |
| **思考档位** | `/thinking` 分档，`samplingParamsByThinkingLevel` 按档位覆盖采样参数 | 自己维护多套参数 |

**结论：从你原计划里直接删掉这些条目** —— provider 适配、模型清单、定价表、对话循环、流式解析、工具调用协议、重试、上下文裁剪、会话存储、密钥管理、token 成本核算。**这不是小节省，这是项目能做完的前提。**

### 关于 models.dev

`models.dev` 是一个**开源的 AI 模型数据库**（provider/model ID、上下文长度、最大输出、是否支持图片/工具、开源闭源、输入输出价格、发布/更新日期）。它和 Pi 自带 catalog 是同类数据，可以这样配合：

- **日常**：只用 Pi 自带 catalog + `pi update --models`，别的都不用管；
- **要更细的定价/新模型**：写个 20 行脚本把 models.dev 的条目灌进 `modelOverrides`（Pi 支持改内置模型的元数据而不替换 provider 的模型列表）；
- **自建端点**：在 `models.json` 里手写一条，元数据照 models.dev 抄。

> 不要去「收集 provider 信息」——那是纯体力活，且永远过时。你只需要在**一个** `models.json` 里写你实际会用的那 2–3 个端点。

## 3. 你唯一要写的 AI 相关代码：一个薄网关

Pi **没有官方 server 模式**（`pi-server` 已被 1.2.0 移除），SDK 是 Node/TS 库，Android 直连不了。所以要一层网关——但**它只有 ~200–300 行，是传输层，不是 AI 层**。

```
Android ──HTTP/SSE──> 你的网关(Node/TS) ──SDK──> Pi（进程内）──> provider
                              │
                    你自己的工具实现 ──HTTP──> FastAPI 业务服务 ──> PostgreSQL
```

网关要做的全部事情：

```ts
// 伪代码，全部逻辑就这些
const session = await createAgentSession({ sessionDir: '/data/pi-sessions', /* ... */ });

app.post('/agent/chat', async (req, res) => {
  res.sse();                                  // 1. 开 SSE
  const sub = session.subscribe(ev => res.send(ev));  // 2. 把 Pi 事件原样转发
  await session.prompt(req.body.text, { images: req.body.images });  // 3. 发一轮
  sub.close(); res.end();                     // 4. 结束
});

app.get('/agent/entries', async (req, res) => {
  res.json(await session.getEntries({ since: req.query.since }));   // 增量：entry id 是持久游标
});
```

**网关不做的事**（防止它变成新的「底层」）：不做 prompt 拼接、不做工具实现、不做模型选择、不做重试策略、不做 token 计算——**全部透传或交给 Pi**。

## 4. 关键洞见：Pi 不需要内置记忆，因为**你的工具就是它的记忆**

我上一版把「Pi 无内建长期 memory」列为风险，这个判断在你的场景里是**错的**。原因是：

通用 agent 需要「记忆层」，是因为它没有别的数据源。**而你的 agent 有数据库。**

```
用户问："我电磁感应老错，根因在哪？"
   ↓
Pi 调用工具 kp_prereq_chain(kp_id="电磁感应")
   ↓
你的 FastAPI 查 PostgreSQL：先修边 + 掌握度 + 错题分布
   ↓
返回结构化事实："磁场对电流的作用 mastery=0.31，是你 3 周前错的那道题的根因"
   ↓
Pi 组织成回答
```

**掌握度、错题、复习历史全部住在你的数据库里，通过工具暴露给 Pi。** Pi 的会话 JSONL 只负责「这次对话说过什么」，长期知识根本不归它管。

这带来三个好处：
1. **Pi 换代/重装，你的学习数据一点不丢**（数据在 PG，不在 Pi 的会话文件里）；
2. **同一个知识图谱可以同时服务 App 的今日队列、周报统计、和 Pi 的问答**——不用为 AI 单独准备一份「记忆」；
3. **你不需要 RAG 式的向量堆砌**：查库比检索更准、更便宜、可解释。

> 一句话：**Pi 给的是「大脑」，你给的是「记忆」和「手脚」。** 这个分工比让 Pi 自己攒记忆干净得多。

## 5. 工具清单（这是你真正要写的核心工作）

设计原则三条，先立规矩再列清单：

1. **默认只读**。读工具随便调，写工具必须显式。
2. **写操作默认落「待你确认」队列**（除对话沉淀这种可撤销的）。理由：**一次错误的自动写入会污染整个知识图谱**，而污染比缺失难修得多。
3. **不可逆操作（删除、合并、覆盖已确认字段）不给 agent 开工具**。你要删，自己在 App 里点。

### 5.1 读工具（P0，先把这些做出来）

| 工具 | 作用 | 关键参数 | 对应你的哪个痛点 |
|---|---|---|---|
| `kp_search` | 按名字/别名找知识点 | `query, subject?, limit` | 知识点串联 |
| `kp_get` | 知识点详情：掌握度、上下级、挂了多少题、最近错几次 | `id` | 知识点串联 |
| `kp_prereq_chain` | **先修闭包**：「根因在哪」 | `id, depth=2` | ★ 知识点串联的核心 |
| `kp_weakest` | 最薄弱的 N 个知识点（按掌握度 + 遗忘天数加权） | `subject?, limit` | 主动关心 |
| `question_search` | 多条件找旧题：关键词/知识点/错因/时间/有没有图 | `q?, kp_ids?, error_type?, from?, to?, limit, cursor` | ★「以前做过哪一题」 |
| `question_get` | 题目全文 + 答案 + 解析 + 历次作答 | `id` | 同上 |
| `mistake_list` | 待解决的错题 | `status?, kp?, limit` | 错题收集 |
| `mistake_get` | 错题详情：错因、你的原话备注、重做记录 | `id` | 错题收集 |
| `attempt_history` | 某题做过几次、哪次对哪次错、隔了多久 | `question_id` | 遗忘判断 |
| `due_queue_preview` | 今日队列（只读视图，不改调度） | `limit` | 帮 agent 回答「今天练什么」 |
| `stats_summary` | 周报数据：新增/复习量、掌握度升降 Top、重犯错因 | `subject?, days=7` | 学习变化 |
| `image_get` | 取题目/错题的原图（配合 Pi 的图片输入） | `question_id` | 看图讲题 |

### 5.2 写工具（P0/P1，全部走确认）

| 工具 | 作用 | 闸门 |
|---|---|---|
| `question_upsert` | 新建题目（题干/答案/解析/选项） | **新建直接入库**；改已有题目 → 生成 patch 进待确认 |
| `question_attach_kp` | 题目挂知识点（1 主 + N 辅 + 权重） | 直接写，可撤销 |
| `mistake_record` | 记一次「我错了」+ 错因 | 直接写 |
| `kp_upsert` | 新建知识点 | 直接写 |
| `kp_edge_add` | 加先修边 | **服务端做环检测**，成环拒绝 |
| `card_create` | 从题目/知识点生成复习卡 | 直接写，但**不自动评** |
| `note_write` | 写一条学习笔记（Markdown） | 直接写 |
| **`deposit_from_chat`** | **把本轮对话沉淀成待复习条目**（知识点 + 错因 + 你的原话片段） | **直接写**，App 里有「撤销」按钮 |

> `deposit_from_chat` 是整个产品的差异化落点，也是唯一一个「写」得不该有摩擦的工具。它的调用时机应该是：**回答结束之后异步跑一次**，不打断你阅读。产出 1–3 条，默认已加、可撤销。

### 5.3 不给 agent 开的

- 删除题目/知识点/错题
- 合并知识点（跨学科合并尤其危险）
- 改已确认的答案字段
- 改 FSRS 评分（评分只能你按）
- 改用户配置

### 5.4 工具多了怎么办：**打开 `tool-search`**

Pi 内置四个扩展：`mcp` / `llama.cpp` / `codemode` / **`tool-search`**。上面这张表 P0 就有 ~20 个工具，**把全部 schema 塞进每次请求会白烧 token，也容易选错工具**。

→ 工具数超过约 15 个时，启用 `tool-search`，让模型按需检索工具再调用。

## 6. 模型与 provider 配置（你实际要写的全部）

### 6.1 用自带 catalog

```bash
pi update --models        # 刷新 catalog；离线时用缓存
```

然后 `/login` 或设环境变量，`/model` 里就有得选。**这一段你什么都不用维护。**

### 6.2 你要写的那一个 `models.json`

假设你用 DeepSeek + 一个中转，按文档字段拼（**第一次跑要核对 schema**，`$schema` 指 `https://pi.dev/schemas/models.schema.json`）：

```json
{
  "$schema": "https://pi.dev/schemas/models.schema.json",
  "providers": {
    "deepseek": {
      "baseUrl": "https://api.deepseek.com/v1",
      "api": "openai-completions",
      "apiKey": "$DEEPSEEK_API_KEY",
      "models": [
        {
          "id": "deepseek-v4-flash",
          "reasoning": false,
          "promptCache": { "short": 300 },
          "inputLimits": {
            "images": { "resize": { "maxWidth": 1568, "maxHeight": 1568, "maxBytes": 524288, "jpegQuality": 75 } }
          }
        }
      ]
    }
  }
}
```

三个字段值得解释，因为它们**直接省钱**：

- `promptCache.short: 300` —— 声明「这个 provider 的缓存存活 5 分钟」，Pi 才会做 **cache warming**。你的系统提示 + 工具 schema 每次都在，缓存命中后长提示的输入价能低到 1/10 量级。**不声明这个字段，Pi 就不会去预热缓存。**
- `inputLimits.images.resize` —— 题目照片动辄 4MB，压到 1568px/512KB 再送，token 和延迟都降一个量级。
- `reasoning: false` —— 学习问答多数场景不需要思考链，关掉省 token。

### 6.3 想改价目/换模型

用 `modelOverrides` 改内置模型的元数据（不改 provider 的模型列表）；未知 override ID 会被忽略——这个行为是安全的。

## 7. 会话映射

| 你的概念 | Pi 的概念 | 理由 |
|---|---|---|
| 一个学科（或一个学习主题） | **一个 Pi session** | 长期存在，compaction 和上下文累积才有意义 |
| 一次提问 | 一次 `session.prompt()` | |
| 一轮回答产出的事实 | **你的数据库**（不是 Pi 的记忆） | 见 §4 |
| 手机断线重连 | `get_entries(since: <entryId>)` | entry id 是**持久游标**，重启后仍只取新增 |
| 「换个问法重来」 | `fork` / `clone` | 不丢原历史 |

**并发注意**：**单个 session 同时只能有一个活跃 run**。流式输出期间再发消息必须显式 `streamingBehavior: "steer" | "followUp"`，否则报错。单人使用压力小，但 App 端要有「上一条还没答完」的排队处理，别让用户狂点。

## 8. 剩下两个真风险（不是「别用 Pi」，是「用的时候注意」）

| 风险 | 对策 |
|---|---|
| **迭代快、破坏性变更多**（1.0.0 → 1.5.2 六周 8 个 minor） | ① **package.json 锁精确版本**，`npm ci` 不用 ranges；② 网关只依赖 `createAgentSession / subscribe / prompt / getEntries` 四个 API，其余一律不碰（**接口面越小，升级越无痛**）；③ 升级前在 git worktree 里跑一遍冒烟测试 |
| **默认人设是「编码 agent」**：内置工具是 read/bash/edit/write，系统提示偏编程 | ① `defaultTools` 收紧到只留 `read` + 你的工具；② 用 `SYSTEM.md` / `APPEND_SYSTEM.md` 覆盖成「学习教练」人设（注意这两类文件**不受 project trust 约束**，一定放在你自己的目录里）；③ 学科方法论写成 skills，惰性加载 |

补充一条部署安全：**Pi 没有内置沙箱**，工具以进程权限执行。→ 跑在容器里、用低权用户、工具实现里对所有参数做校验（尤其是 `kp_edge_add` 的环检测、`question_upsert` 的字段白名单）。

## 9. 项目层面的净收益（修正 05 的工时）

| 里程碑 | 原估 | 现在 | 变化原因 |
|---|---|---|---|
| M4 提问沉淀 | 1–2 周 | **3–5 天** | 对话循环/provider/流式/会话全部由 Pi 承担，你只写沉淀抽取 + 工具 |
| M0 骨架 | 1 周 | 1 周 | 不变（多了 `agent/` 目录和网关） |
| M1 录入闭环 | 2–3 周 | 2–3 周 | 不变（OCR 与 Pi 无关） |
| **总计（到 M5）** | 100–150 h | **≈ 80–120 h** | |

**省下来的不是「写代码的时间」，是「调试 AI 底层的时间」**——后者才是真正会拖垮单人项目的部分。

## 10. 一天的验证（动工前先做这个）

```bash
# 1. 起一个 Pi，确认 catalog 里有你要的模型
npm i -g @earendil-works/pi-coding-agent   # 锁版本，此处仅示意
pi update --models
# 2. 写一条 models.json，指向你的中转/DeepSeek，跑通一轮问答
# 3. 写一个 30 行的自定义 tool（比如 kp_search 的假实现），确认 Pi 能调用它
# 4. 用 SDK 起一个 Node 脚本：createAgentSession → subscribe → prompt → 读到流式事件与工具结果
# 5. 发一次 session.getEntries()，确认 entry id 能当增量游标
```

**这五步跑通，就证明「Pi 当底层 + 你只写工具」这条路是真的。** 跑不通，问题也会暴露在最便宜的位置——而不是在三个月后。
